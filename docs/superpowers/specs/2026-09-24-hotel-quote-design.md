# 代订酒店报价 · 设计 Spec

> 状态：已与需求方确认（2026-09-24）。基于 xy-dsh-robot 现有架构增量扩展。

## 1. 目标

客户在闲鱼私信发「酒店名 + 入住日期 + 晚数（+可选房型/人数/含早/取消政策）」，
机器人自动完成：多源比价（携程/同程/酒店官网公开价，v1 由 dsh agent 动态查询）
→ 按阶梯加价策略报价 → 引导成交 → 付款后人工在会员/代理渠道下单 → 回填确认号
→ 自动发货并确认交易。

**边界（与全系统一致的铁律）**：
- 查价/报价/聊天全自动；**真实下单与付款永远人工**；
- 会员/协议价 v1 走「人工补价通道」（后台标注成本价，报价优先采用），
  v1.5 再做官网 Cookie 会话自动查询（复用扫码抓取基建）。

## 2. 用户已拍板的决策

| 决策项 | 结论 |
|---|---|
| 成本渠道 | 双轨：酒店会员/协议价（人工补价起步）+ 公开价+服务费 |
| 卖价模式 | 阶梯百分比加价（默认 ≤¥500→10%、¥500–1500→8%、>¥1500→5%，config 可调） |
| 查价实现 | v1 纯 dsh agent 动态查询（web 工具），不做逆向/浏览器自动化 |

## 3. 流程（SOP-6 sop-hotel-quote）

```
chat(意图=代订询价)
  → ① 要素解析：酒店名/入住日/晚数 必收；房型/人数/含早/取消政策 可选
      缺必收 → 一次性反问补全
  → ② 查价：命中缓存(酒店+日期+房型, TTL 30min)直接用；否则 agent 查
      携程/同程/官网公开价 → 结构化 JSON{source, price, breakfast, cancel_policy}
  → ③ 报价：成本=min(可订价，人工补价优先) → 卖价=成本×(1+阶梯加价)
      >¥2500 不自动报价转人工
  → ④ 报价话术（必含）：价格、含早与否、退改口径、"10 分钟内有效、以最终确认为准"
  → ⑤ 客户接受 → 引导拍「酒店代订」服务商品 → reprice 到报价（走既有改价闸门）
  → ⑥ 付款卡片 → 转人工事件：渠道下单（人工付款）→ 后台回填确认号
  → ⑦ 回填后自动发货（内容=确认号）→ 自动确认交易（走既有七道闸门）
```

## 5. 报价闸门（代码强制）

1. 查价限频：每会话每小时 ≤3 次全量比价（防 OTA 风控 + 防刷）；
2. 缓存 TTL 30 分钟（默认）；
3. 成本 > ¥2500（默认）→ action=block（转人工核价），agent 不得自行报价；
4. 报价话术三要素（有效期/含早/退改）由提示词约束，金额与有效期由闸门回填给 agent。

## 6. 错误与降级

- 单源查询失败：用其余源继续；三源全失败 → 回复"稍等，人工核价"并转人工事件；
- OTA 反爬/验证码：该源标记失败不重试（同闲鱼纪律），当日同源熔断 30 分钟；
- 客户在报价 10 分钟后要求成交：按 SOP 重新查价或转人工，不吃旧价。

## 7. 测试

- 单测：要素解析（正反例）、`calc_quote` 阶梯矩阵、闸门（限频/阈值/缓存命中/过期）、人工补价读写；
- E2E：`e2e/run_e2e.py` 追加 1 步——通过 `/api/chat` 发"帮我查杭州XX酒店 10月1日 2晚"（dry-run，agent 真查价真报价，验回复含价格与有效期条款）；
- 回归：39 个既有单测全绿。

## 8. 非目标（本轮不做）

- 携程/同程逆向 API、浏览器自动化查价（方案 B/C，量大再上）；
- 官网会员/协议价自动登录查询（v1.5，复用扫码基建后逐连锁接）；
- 自动下单/自动支付（永久不做）；
- 独立报价管理页面（v1 只做设置页补价入口 + 事件台账）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| OTA 价格分钟级波动 → 价差纠纷 | 报价有效期 10 分钟 + "以最终确认为准"条款 + 成交前可重查 |
| agent 查 OTA 触发反爬 | 限频 + 缓存 + 单源熔断 + 当日查询总量上限（默认 60 次/日） |
| 协议价转售合规（灰色） | 话术不出现"协议价"字样；会员价以"渠道优惠价"表述 |
| 大额单风险 | >¥2500 强制转人工 |
